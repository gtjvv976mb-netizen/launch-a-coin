# Launch a Card

Source repository: [gtjvv976mb-netizen/launch-a-coin](https://github.com/gtjvv976mb-netizen/launch-a-coin). The repository's existing name is retained; the platform is branded **Launch a Card**.

Independent project based on MintDex, publicly branded **Launch a Card** at **https://launchacard.fun**. The recoverable folder and internal carddex identifiers remain stable. Creators choose one permanent premium card design for their token and its one-of-one NFT trading card. The token launch provider is **pump.fun**.

## Run locally

Requires Node22+, Bun and Chrome for optional QA.

```sh
cd integrations/pumpfun
bun install --frozen-lockfile
cd ../../app
bun install --frozen-lockfile
bun run dev
```

This builds the Worker, applies **local-only** D1 migrations and starts the local preview at **http://127.0.0.1:5310**. Subsequent starts can use `bun run preview`. Runtime state is inside ignored `app/.wrangler/`. Test accounts use an independent `carddex_session` cookie.

```sh
bun test tests/chain tests/carddex
bun run build
```

`bun run build` waits for both TypeScript and Vite, and compares shared source/config/asset fingerprints before and after the client/SSR build. Finish edits before building; an input change rejects the build so mixed client/server output is not treated as ready. Ensure Bun is on the shell's PATH. In this workspace the helper can also be invoked directly with `~/.bun/bin/bun scripts/build.mjs`.

See `HANDOFF.md` and the dated reports for the latest build/test counts and browser evidence. The local database must have all migrations applied before starting the current preview.

The [29 October card-consistency audit](reports/launch-a-card-card-consistency-2026-10-29.md) reviews all 48 designs and 83 atlas variants. Corrections remove a creator-art offset/color tint, match export data typography and keep Home's card visible on short landscape phones. They use renderer `launchacard-canonical-v2.1` and preserve saved launch images, with244 passing tests. The audit initially stopped in preview; the owner's subsequent instruction authorized the [publication follow-up](reports/launch-a-card-card-consistency-release-2026-10-29.md).

## Current status and real pump.fun launches

The public `/launch` route is enabled for the **real mainnet creator-wallet flow**, with an explicit **Test demo** option. Local configuration remains disabled and isolated. The directory, portfolio and token trading catalogue remain clearly marked demo; they do not invent on-chain balances. Both inherited `VITE_MINTDEX_MODE` and `VITE_CARDDEX_MODE` activation remain rejected. The new wallet integration is separate from the inherited MintDex program.

`integrations/pumpfun` uses the pinned official pump.fun SDK to prepare a complete create_v2 transaction with the selected admitted quote and optional exact-amount initial buy. It revalidates mainnet genesis, quote admission, mint/program/decimals, balances, rent and fresh transaction simulation. Native SOL and 36 custom quote assets are supported, subject to current on-chain admission and packet limits. A requested initial buy is never silently dropped.

The browser generates ephemeral token/NFT signers in memory, authenticates wallet ownership with a labelled message, and checks the exact immutable transaction before wallet approval. The server validates every signature and the exact prepared bytes, simulates and relays those same wallet-signed bytes. Token finalization is independently verified before a separate **Metaplex Core NFT** transaction is prepared. The NFT is owned by the creator, has immutable metadata and binding attributes, and has no royalties plugin. Durable intents, concurrency guards and recovery prevent an interrupted NFT stage from creating another token or duplicate NFT.

The trusted server image composer uses the same canonical card layout and preflattened approved skins, actual creator artwork and a premium rounded case. Content-addressed public metadata binds creator, token mint, quote mint, design, original frame/back hashes and rendered image hashes. Client-provided finished images cannot qualify as an attested composition.

No real transaction was signed or submitted. Public-mainnet read-only simulations verified create_v2 and Core creation against the actual programs. These are simulations, not completed token/NFT issuance. A first owner-approved launch is still required after public deployment.

Two switches in `app/wrangler.production.jsonc` control the live flow, both read trimmed and in any case. `CARDDEX_LIVE_LAUNCH_ENABLED="true"` opens new launches (card composition, a new launch and its coin transaction). `CARDDEX_LIVE_RECOVERY_ENABLED` stays on unless it is `"false"`, `"0"`, `"off"` or `"no"`; it covers sign-in, saved launches, confirmations, the card stage and discards (sign-out always works). To stop new launches, turn off only the first switch: creators with a coin already sent can still finish their card. `/api/live/health` reports both.

Platform limits. Every live action that costs RPC calls, R2 writes or D1 rows is limited per wallet and, where throwaway wallets could share one client, per connecting address (`app/src/lib/carddex/live/limits.server.ts`, D1 table `rate_events`, migration `0014`); an IPv6 address counts as its /64, and clients are stored only as HMAC hashes under a random per-deployment key. The initial-buy size check and new sessions are limited per address too, since a fresh keypair signs in for free. The demo's free accounts and public art uploads are limited per address and with a site-wide hourly ceiling. A wallet's ownership challenge can never be used to lock its owner out: past its limit the newest open challenge is handed back. Launch images and metadata are public in three steps (`live_assets.published_at`, `public_until`, migration `0015`): a bare upload is served only to its uploader and the Worker's own verification read; a saved launch makes them public for one hour, so the wallet prompt can show the coin; the creator's signed coin transaction (saved before it is sent) makes them public for good. Rows an older Worker stored stay public, so a launch saved while migrations ran ahead of the deploy keeps its metadata. A launch stage that was prepared more than 120 times is slowed to one new plan every three minutes, never closed, so a coin that landed can always get its card. Request bodies are capped at the Worker entry (64 KiB for server functions, 5 MiB for composition, 6 MiB for demo uploads). A saved launch always loads: a coin that failed on Solana or expired unlanded says so and can be prepared again with the same mint once nothing it signed can still land, and confirmation checks send saved signed bytes again while they can land. Each stage change and refusal logs one `live_launch_event` line (ids and reasons only); the saved-launch panel shows the first 8 characters of the launch id as a support reference. `CARDDEX_MIRROR_REDIRECT="true"` sends page views on mirror hosts (workers.dev, launchacard.com, edge.launchacard.com) to launchacard.fun; leave it unset until launchacard.fun is reachable from every network. Proposed production config (rate-limit binding, observability, cron) is in the audit's `proposed-config.md`.

Signing order. For wallets named in `CARDDEX_LIVE_WALLET_FIRST` (unset means Phantom only; a comma list of wallet names, `"*"` for all, or `"none"`), the wallet signs the unsigned coin or card transaction first and the page then adds the new address's signature, the order Phantom documents for multi-signer transactions. Every other wallet keeps the page-first order. Phantom may append read-only Lighthouse assertions and refresh the blockhash: the page co-signs those only within the shared wallet rule (`integrations/pumpfun/src/wallet-guards.ts`), the server applies the same rule, checks a refreshed blockhash is still valid, and stores the signed message hash and its expiry bound before any broadcast. If a wallet returns anything else, the page sends nothing, the server logs `Live wallet changed the prepared transaction` with what changed (sizes, blockhash, compute budget, programs added, and the rule's answer), and the wallet opens once more with the page signing first. Set `"none"` to restore the page-first order everywhere without a code change. Every launch transaction also logs `Live launch transaction prepared` and `... signed` with its byte size and headroom under the 1,232-byte limit. A plan older than about 30 seconds is prepared again before the wallet opens.

Wallet prompts. Pressing Launch with no wallet connected opens the wallet list, and the launch then continues on its own. A wallet with `solana:signIn` (Phantom, MetaMask and Backpack register it) connects and proves its owner in one Sign In With Solana prompt; the request carries every field (this site's host and origin, `Chain ID: mainnet`, a single-use nonce from a wallet-independent, per-client rate-limited challenge, a 5-minute expiry), and the page and the server both check the wallet's text the way `verifySignIn` does before the same 2-hour session starts. Any other wallet, or a wallet that signs other text, uses the connect and ownership-message route as before. For wallets named in `CARDDEX_LIVE_WALLET_BATCH` (unset means none: one approval is opt-in per wallet after a prompt-and-reject test on the live site, with `"Backpack"` the candidate; the same comma list, `"*"` or `"none"`; Phantom is never batched, because Phantom blocks multi-transaction requests from sites it has not reviewed), the coin and its card are prepared together and signed in one approval. The card's signed bytes are saved on the server before the coin is sent (a closed tab resumes with "Send your approved card") and are relayed only after the coin's finalized verification. If the card's blockhash runs out first, its own review opens and the wallet asks once more; nothing is charged for the expired card. A wallet that does not return both, or fails the request for any reason other than the person's refusal, falls back to the coin alone. Prompt counts from a first press of Launch: Phantom and Backpack 3 (sign-in, coin, card; Backpack 2 once it is listed for one approval), a wallet without sign-in 4. Phantom's sign-in on launchacard.fun that fails with -32000 falls back to the ownership message.

Deploying this build: run `wrangler d1 migrations apply launch-a-card --remote` (migrations `0012` to `0015`) and then deploy, as one step. `/api/live/health` reports `schema.missing` until every migration is applied, and is not `ok` before that; the request limits log one error and let requests through rather than fail them.

### Wallet notices only reviews can clear

Code removes every warning cause it controls: both transactions simulate cleanly before the wallet opens, carry both compute-budget instructions, stay at least 160 bytes under the packet limit (every coin transaction loads pump.fun's own create lookup table), the wallet signs first where Phantom asks for it, and the server sends through its own RPC with preflight. Four notices remain that only the wallets' reputation reviews can clear:

1. Phantom's yellow new-domain banner on launchacard.fun (usually clears by itself within a few days).
2. The new coin shown as unverified (Phantom shows CoinGecko and Jupiter verification; a brand-new pump.fun coin has none).
3. A possible Phantom red "Request blocked" screen for multiple signers: both transactions need two signers (pump.fun's create_v2 needs the new mint's signature, Metaplex Core the new asset's), exactly like pump.fun's own creates.
4. Blockaid verdicts for a new domain in Backpack, Jupiter Wallet, MetaMask and Coinbase Wallet.
