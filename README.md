## Run locally

Requires Node22+, Bun and Chrome for optional QA.

```sh
cd integrations/pumpfun
bun install --frozen-lockfile
cd ../../app
bun install --frozen-lockfile
bun run dev
```

This builds the Worker, applies **local-only** D1 migrations and starts the local preview at **http://127.0.0.1:5310**. Subsequent starts can use `bun run preview`. Runtime state is inside ignored `app/.wrangler/`. Test accounts use an independent `carddex_session` cookie.

```sh
bun test tests/chain tests/carddex
bun run build
```

`bun run build` waits for both TypeScript and Vite, and compares shared source/config/asset fingerprints before and after the client/SSR build. Finish edits before building; an input change rejects the build so mixed client/server output is not treated as ready. Ensure Bun is on the shell's PATH. In this workspace the helper can also be invoked directly with `~/.bun/bin/bun scripts/build.mjs`.

See `HANDOFF.md` and the dated reports for the latest build/test counts and browser evidence. The local database must have all migrations applied before starting the current preview.

The [29 October card-consistency audit](reports/launch-a-card-card-consistency-2026-10-29.md) reviews all 48 designs and 83 atlas variants. Corrections remove a creator-art offset/color tint, match export data typography and keep Home's card visible on short landscape phones. They use renderer `launchacard-canonical-v2.1` and preserve saved launch images, with244 passing tests. Two switches in `app/wrangler.production.jsonc` control the live flow, both read trimmed and in any case. `CARDDEX_LIVE_LAUNCH_ENABLED="true"` opens new launches (card composition, a new launch and its coin transaction). `CARDDEX_LIVE_RECOVERY_ENABLED` stays on unless it is `"false"`, `"0"`, `"off"` or `"no"`; it covers sign-in, saved launches, confirmations, the card stage and discards (sign-out always works). To stop new launches, turn off only the first switch: creators with a coin already sent can still finish their card. `/api/live/health` reports both.

Platform limits. Every live action that costs RPC calls, R2 writes or D1 rows is limited per wallet and, where throwaway wallets could share one client, per connecting address (`app/src/lib/carddex/live/limits.server.ts`, D1 table `rate_events`, migration `0014`); an IPv6 address counts as its /64, and clients are stored only as HMAC hashes under a random per-deployment key. The initial-buy size check and new sessions are limited per address too, since a fresh keypair signs in for free. The demo's free accounts and public art uploads are limited per address and with a site-wide hourly ceiling. A wallet's ownership challenge can never be used to lock its owner out: past its limit the newest open challenge is handed back. Launch images and metadata are public in three steps (`live_assets.published_at`, `public_until`, migration `0015`): a bare upload is served only to its uploader and the Worker's own verification read; a saved launch makes them public for one hour, so the wallet prompt can show the coin; the creator's signed coin transaction (saved before it is sent) makes them public for good. Rows an older Worker stored stay public, so a launch saved while migrations ran ahead of the deploy keeps its metadata. A launch stage that was prepared more than 120 times is slowed to one new plan every three minutes, never closed, so a coin that landed can always get its card. Request bodies are capped at the Worker entry (64 KiB for server functions, 5 MiB for composition, 6 MiB for demo uploads). A saved launch always loads: a coin that failed on Solana or expired unlanded says so and can be prepared again with the same mint once nothing it signed can still land, and confirmation checks send saved signed bytes again while they can land. Each stage change and refusal logs one `live_launch_event` line (ids and reasons only); the saved-launch panel shows the first 8 characters of the launch id as a support reference. `CARDDEX_MIRROR_REDIRECT="true"` sends page views on mirror hosts (workers.dev, launchacard.com, edge.launchacard.com) to launchacard.fun; leave it unset until launchacard.fun is reachable from every network. Proposed production config (rate-limit binding, observability, cron) is in the audit's `proposed-config.md`.

Signing order. For wallets named in `CARDDEX_LIVE_WALLET_FIRST` (unset means Phantom only; a comma list of wallet names, `"*"` for all, or `"none"`), the wallet signs the unsigned coin or card transaction first and the page then adds the new address's signature, the order Phantom documents for multi-signer transactions. Every other wallet keeps the page-first order. Phantom may append read-only Lighthouse assertions and refresh the blockhash: the page co-signs those only within the shared wallet rule (`integrations/pumpfun/src/wallet-guards.ts`), the server applies the same rule, checks a refreshed blockhash is still valid, and stores the signed message hash and its expiry bound before any broadcast. If a wallet returns anything else, the page sends nothing, the server logs `Live wallet changed the prepared transaction` with what changed (sizes, blockhash, compute budget, programs added, and the rule's answer), and the wallet opens once more with the same unsigned transaction (prepared again if stale), still wallet first; a second refusal stops with nothing sent. A wallet-first wallet never falls back to the page signing first: Phantom support confirmed its "This dApp could be malicious" warning appears when another signature is already on a transaction before Phantom signs. Before any wallet prompt the server simulates the unsigned transaction with `sigVerify: false`, and it relays with preflight on (`skipPreflight: false`, `preflightCommitment: "confirmed"`). Set `"none"` to restore the page-first order everywhere without a code change. Every launch transaction also logs `Live launch transaction prepared` and `... signed` with its byte size and headroom under the 1,232-byte limit. A plan older than about 30 seconds is prepared again before the wallet opens.

Wallet prompts. Pressing Launch with no wallet connected opens the wallet list, and the launch then continues on its own. A wallet with `solana:signIn` (Phantom, MetaMask and Backpack register it) connects and proves its owner in one Sign In With Solana prompt; the request carries every field (this site's host and origin, `Chain ID: mainnet`, a single-use nonce from a wallet-independent, per-client rate-limited challenge, a 5-minute expiry), and the page and the server both check the wallet's text the way `verifySignIn` does before the same 2-hour session starts. Any other wallet, or a wallet that signs other text, uses the connect and ownership-message route as before. For wallets named in `CARDDEX_LIVE_WALLET_BATCH` (unset means none: one approval is opt-in per wallet after a prompt-and-reject test on the live site, with `"Backpack"` the candidate; the same comma list, `"*"` or `"none"`; Phantom is never batched, because Phantom blocks multi-transaction requests from sites it has not reviewed), the coin and its card are prepared together and signed in one approval. The card's signed bytes are saved on the server before the coin is sent (a closed tab resumes with "Send your approved card") and are relayed only after the coin's finalized verification. If the card's blockhash runs out first, its own review opens and the wallet asks once more; nothing is charged for the expired card. A wallet that does not return both, or fails the request for any reason other than the person's refusal, falls back to the coin alone. Prompt counts from a first press of Launch: Phantom and Backpack 3 (sign-in, coin, card; Backpack 2 once it is listed for one approval), a wallet without sign-in 4. With a creator fee split (below) each count is one higher: Phantom 4 (sign-in, coin, card, split). Phantom's sign-in on launchacard.fun that fails with -32000 falls back to the ownership message.

Creator fee sharing (pump.fun's own fee split; branch `claude/fee-sharing`, not deployed). Its own kill switch, `CARDDEX_LIVE_FEE_SHARING`, is on only for `"true"` (trimmed, any case); unset, the default and every local preview, is off. Readiness reports it as `feeSharing` (on only with recovery ready too); off, Launch hides the "Share creator fees" group in More options and the server refuses a new launch that carries a split and every fee split action except confirming a split already sent (preparing, sending and skipping are all refused). A saved launch that chose a split can still be prepared again while it is off: its split is checked against the saved one, stays `requested`, and counts as settled until the switch is on again. On, a creator may choose 1 to 7 Solana wallets (on the ed25519 curve, so never a program address; never the coin, its card, the quote mint or a program; whole basis points adding up to 100%), the first row prefilled with the connected wallet when sharing is turned on. The page checks that every split the server returns (after a launch is prepared, and before the split's own review) is the one chosen in that tab, and every review lists each recipient's full address. The split is saved beside the launch (D1 migration `0017`: `live_fee_shares`, one row per launch with its recipients frozen by trigger, and `live_fee_share_transactions`, one row per prepared attempt with the plan and signed bytes frozen as in `0011`/`0012`), never in its payload, request hash or binding, so saved launches verify byte for byte. Once the coin and card are complete, a third, creator-only transaction sets it: 2 compute-budget instructions, pump `sweep_creator_fee` (fees earned so far go to the creator's own pump.fun vault first, so they stay the creator's), pump-fees `create_fee_sharing_config`, on a token pair one idempotent ATA create for the sharing vault's quote account, then `update_fee_shares` (SOL) or `update_fee_shares_v2`, which locks the split for good (verified by unsigned mainnet simulation on 31 October 2026: a second update fails 6009). The creator is its only signer, so the wallet only ever sees unsigned bytes and the page adds nothing. It costs a network fee and rent for pump.fun's 1,024-byte sharing config (5,852,160 lamports), plus 1,488,440 lamports for the vault token account on a token pair; a wallet short of that is told before simulation. Seven recipients is the most that fits the 1,072-byte wallet target with the config create on every pair, using pump.fun's lookup table with four more pinned entries (5, 6, 13, 151: AMM program, AMM event authority, ATA program, pump-fees event authority); a create-only coin prepared from now on is 31 bytes smaller for the same reason, and browser and server ship the pin list together. A graduated coin is refused and pointed to pump.fun. A recipient that is a program (pump.fun's payout would fail 6052 for everyone, forever) or an account holding data is refused; an empty wallet is allowed (pump.fun holds its share until it covers rent). "Skip, keep 100%" asks first, then records pump.fun's default for good; the server reads the coin's split before recording it, so a split that is locked after all is recorded as set instead. A sent split that expired is read from the chain only once finalized block height is past its saved expiry, at that finalized bank or newer, so a late landing is never recorded as failed. A coin whose split was set on pump.fun first is recorded as `set_elsewhere` with the split pump.fun pays. Launch a Card is never a recipient and takes no fee. Not offered: holder rewards, mayhem, cashback, `creatorFeeBps`, and social, X or GitHub recipients. Not yet verified: how Phantom and Blockaid present a transaction that calls pump-fees (`pfeeUxB6jkeY1Hxd7CsFCAjcbHA9rWtchMGdZ6VojVZ`); test with a real wallet before switching it on, and switch it on only with explicit authorization.

### Card mint addresses

Each new coin's mint address ends in `card` (as pump.fun's own end in `pump`) while the pool has addresses. The pool is D1 table `live_vanity_mints` (migration `0016`): keypairs the operator grinds locally, each secret key stored only as AES-256-GCM ciphertext under the Worker secret `CARDDEX_VANITY_KEY` (base64 of 32 bytes), bound to its own address. After sign-in, before composing the card, `/launch` asks `issueLiveCardMint` (signed-in creator session and this site's Origin, `no-store`) for one address: one D1 statement moves one `available` row to `issued` for that wallet, so no two requests can get the same key and no key ever goes to a second wallet. A wallet holds at most one issued, unused address: asking again before its launch is saved hands back that same one. The page checks the secret really derives the address and that it ends in `card`, then keeps and signs with it exactly like a random key. Prepare accepts a pool address only from the wallet it was issued to and marks it `used` in the batch that saves the launch. Unset key, empty pool, a limit (6 asks a minute and 10 new addresses a day per wallet; 4 an hour and 10 a day per connecting address, an IPv6 /64 counting as one, since fresh wallets are free; 300 a day site-wide) or any error: the page silently uses a random address, as before. `/api/live/health` adds `vanity: {configured, available, low}` (`low` below 10); it never changes `ok`.

Refill runbook (the owner or operator, on their own machine; never in CI, never in this repo):

1. Grind outside the repo: `mkdir -p ~/lac-vanity/grind && cd ~/lac-vanity/grind && solana-keygen grind --ends-with card:200 --no-bip39-passphrase` (each file is `<ADDRESS>.json`; expect minutes per address).
2. Once, make the key file and keep it (a password manager or other offline backup; losing it makes every unissued row unusable): `bun tools/carddex/vanity-pool.ts --make-key ~/lac-vanity/vanity.key` (mode 600; it is never printed and never overwritten).
3. Once, set the Worker secret from that file, from `app/`: `bun x wrangler@4.147.0 secret put CARDDEX_VANITY_KEY -c wrangler.production.jsonc < ~/lac-vanity/vanity.key`.
4. Build the SQL, from the repo root: `bun tools/carddex/vanity-pool.ts ~/lac-vanity/grind ~/lac-vanity/vanity.key ~/lac-vanity/pool-$(date +%Y%m%d).sql`. Every file must be a 64-byte key whose address (its file name) ends in `card`, or nothing is written; rows are `INSERT OR IGNORE`, so loading an address twice never resets it.
5. Apply migration `0016` first (the deploy step above), then load, from `app/`: `bun x wrangler@4.147.0 d1 execute launch-a-card --remote -c wrangler.production.jsonc --file ~/lac-vanity/pool-<date>.sql`.
6. Check `/api/live/health` shows `vanity.configured: true` and the new `available` count, then delete the SQL and the grind files (the D1 rows are the pool now). Keep only the key file.

Never change the key while rows made under the old one are still `available`: such a row no longer decrypts, so each issue request burns one of them (it is marked `issued` and the page falls back to a random address). To rotate, let the pool run out (or delete its `available` rows), then set the new key and load rows made with it. The repo ignores `*card.json`, `*vanity-key*` and any `.sql` outside `app/migrations`; the tool also refuses to write a key file or SQL inside the repo.
