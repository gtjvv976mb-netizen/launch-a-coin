# 31 October card mint fix pass on `claude/pair-identities` (not deployed)

Review of 3a18402 found one real defect and two small ones; all fixed. Nothing was pushed, deployed, signed or sent; no remote command ran.

- **SEC-VANITY-1 (medium): one address could take the whole 300-a-day site cap.** The per-address rule (30 an hour) allowed 720 a day and fresh wallets are free, so one client with throwaway wallets could take all 300 daily keys. Now: `cardMintIp` 4 an hour plus a new `cardMintIpDay` 10 a day (an IPv6 /64 counts as one), `cardMintWalletDay` 10 a day, site cap unchanged at 300, so one address takes at most 10 a day (30 addresses for the whole cap). A wallet holds at most one issued, unused key: `issueCardMint` hands that same key back to that same wallet (a reload loses the page's copy) without drawing on the daily, address or site budgets, and the issue `UPDATE` adds `AND NOT EXISTS (an issued row for this wallet)`, so concurrent asks from one wallet take one row. A key still never goes to a second wallet. A row that fails its decrypt check is retired (`used` with no launch) so it is never handed back and the wallet's next ask draws a fresh one. Migration `0016` (still unapplied remotely) gains the partial index `live_vanity_mint_issued` on `issued_to WHERE status='issued'`. New log outcome `returned`. Tests: the hand-back and same-wallet concurrency, the new limits, and a one-address drain over a simulated day with a fresh wallet every ten minutes (takes exactly 10; a real creator elsewhere then gets the real key).
- **C1 (low):** the `.gitignore` test in `card-mint.test.ts` is skipped outside a git checkout (an archive or tarball), instead of failing.
- **C2 (low):** `LiveLaunchPanel.prepareDraft` sets `busy` to `preparing` before asking for a card address, so the button shows it is working during that request (up to 8 s) even with no first buy. A source-order test covers it.
- **Not changed (for the lead):** the reviewer's stronger option, never sending the secret to the browser (the Worker would add the mint signature at prepare), is a design change, not made. Many distinct addresses (or many IPv6 /64s) can still together reach the 300-a-day site cap; then launches use random addresses.

**Security notes.** The server (and anyone holding both a D1 copy and `CARDDEX_VANITY_KEY`) knows each pool address's secret until it is used: they could create a coin at an unissued or issued-but-unlaunched address first, which only makes that creator's launch fail its pre-send checks (no funds move; prepare again gives a random or new address). After a coin exists the mint key has no authority (pump.fun's program holds it). The secret reaches the browser once, over HTTPS, `no-store`.
